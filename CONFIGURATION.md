# Manual configuration

Prefer **“Open provider fallback setup”** in your Wingman for the guided setup in 0.4.1. The page handles route JSON, the internal connection and bridge password. This manual alternative also supports the older 0.3.0 package. Both paths use Wingman's existing provider and skill settings; no Core changes are required. See [README.md](README.md).

The setup page uses the existing local Core API on port `49111`; change the advanced **Wingman Core API port** skill setting only if your installation uses another port. Its private link expires after 15 idle minutes. Ask to open setup again if you close or refresh the page. Provider keys are selected by existing Secret names, never entered in the page. Scoped undo is kept in Wingman's generated-files directory, outside this repository; keys are not copied there. Undo retains secrets, including any internal bridge password generated by setup.

## Choose a role

| Role | What it routes | Default | Core setting that uses it |
| --- | --- | --- | --- |
| Main | Conversation requests and the existing Main-model tool flow | Off | Conversation provider: local/OpenAI-compatible, model `waterfall`, endpoint `http://127.0.0.1:4141/v1` |
| Support | Only Support calls Core already schedules, such as memory and summaries | Off | Support Model: Remote, host `http://127.0.0.1`, port `4142` |

Jev remains Wingman's stock decision helper. An optional Main-route tool helper reuses it for an additional first-tool choice; it is off by default and separate from stock command handling. Support has no added Jev helper. Main and Support are independent; either can remain disabled.

## Main setup

1. Back up the Wingman profile/settings and keep the previous skill package.
2. Install `provider_fallback-0.3.0.zip` under `custom_skills`, restart Wingman, and enable **Provider fallback** for the chosen Wingman.
3. In that skill's settings, set `bridge_secret_name` to `local_llm`, configure `routes_json`, then enable **Main fallback**. The Main listener uses loopback port `4141` by default.
4. In Wingman's conversation provider settings, select the local/OpenAI-compatible provider, set endpoint `http://127.0.0.1:4141/v1` and model `waterfall`, and use the same local bridge password stored in Wingman Secrets under `local_llm`.

The local bridge password protects Core-to-Waterfall traffic. It is not an API key for a provider in `routes_json`. Each remote route names an existing Wingman secret in its `secret_name` field. Wingman's `local_llm` secret is shared across Wingmen, so check other profiles before changing it.

## Optional Support setup

Configure this only if you want Waterfall to receive Support work that Core schedules.

1. In the same skill's settings, configure `support_routes_json` and enable **Support fallback**. The Support listener uses loopback port `4142` by default, separate from Main.
2. In Core's Support Model settings, select **Remote**, set **Support Model host** to `http://127.0.0.1` and **Port** to `4142`. Core adds the API path and supplies the `local-model` alias and its fixed local auth value (`not-needed`). Do not append `/v1` to the host or enter a Support API key.
3. Remote Support mode also uses Core's separate remote embedding settings. Keep the existing compatible embedding host, port, and model. Do not point embeddings at the Support listener. If no compatible embedding endpoint is reachable, leave Waterfall Support disabled; this does not affect Main.

The Support listener is infer-only and accepts local model-list and text-completion requests. It does not expose tools, streaming, browser origins, LAN access, status, reset, or admin routes.

## Skill settings

| Property | Default | Meaning |
| --- | --- | --- |
| `main_enabled` | `false` | Enables the Main listener and route chain. |
| `listen_port` | `4141` | Main loopback port. |
| `bridge_secret_name` | empty | Existing Wingman secret name for the Main bridge bearer. |
| `routes_json` | `[]` | Ordered Main provider routes. |
| `fallback_mode` | `credits_only` | Main fallback policy. Old Main profiles without this field retain `availability`. |
| `notify_switches` | `true` | Shows provider switch and recovery notices. |
| `support_enabled` | `false` | Enables the separate Support listener and routes. |
| `support_listen_port` | `4142` | Support loopback port. |
| `support_routes_json` | `[]` | Ordered Support provider routes. |
| `support_fallback_mode` | `credits_only` | Support fallback policy. |

A new install has no active Main or Support route. An enabled role needs a nonempty valid route list. Invalid enabled-role settings produce a visible configuration error; they do not silently choose a provider. Existing Main profiles with routes and a bridge secret remain opted in if they omit `main_enabled`. During upgrade, Core may merge the new `main_enabled: false` default into an older profile. Check **Enable Main fallback** after upgrading if you want to keep Main active.

## Route format

Each route requires `route_id`, a full `endpoint` URL, and `model`. Optional fields include `secret_name`, `request_overrides`, `final_local`, `wire_protocol`, `jev_assist`, `jev_min_confidence`, `omit_request_fields`, and `fallback_on`. Put secret names—not credential values—in route JSON. Generic defaults contain no personal endpoint, model, or secret reference.

```json
[
  {"route_id":"preferred","endpoint":"https://api.anthropic.com/v1/messages","wire_protocol":"anthropic_messages","model":"YOUR_MODEL_ID","secret_name":"YOUR_SECRET_REFERENCE"},
  {"route_id":"backup","endpoint":"https://api.openai.com/v1/chat/completions","model":"YOUR_MODEL_ID","secret_name":"YOUR_SECRET_REFERENCE"},
  {"route_id":"local","endpoint":"http://127.0.0.1:11434/v1/chat/completions","model":"YOUR_LOCAL_MODEL","final_local":true}
]
```

Replace placeholders with the provider's supported endpoint, exact model ID, and existing Wingman secret name. Local or remote OpenAI-compatible servers may be used. The `final_local` route is optional and, when set, must be last. A configured endpoint does not prove provider compatibility or supported image, tool, or parameter behavior.

For stock Wingman Support completions, use `wire_protocol: "wingman_support"` and a provider-documented full endpoint ending in `/support/completions`. Other routes use a supported protocol such as `openai_chat` or `anthropic_messages`. `omit_request_fields` can remove selected optional inherited sampling fields a route does not support. It cannot remove required messages, the model, or the completion contract. Unsupported protocols and malformed route settings fail explicitly.

`request_overrides` cannot replace messages, tools, tool choice, model, or streaming mode. Anthropic's OpenAI-compatible endpoint, for example, does not honor OpenAI `reasoning_effort`.

## Fallback and billing

Enabling a role permits its configured routes to make provider calls; API charges may apply on any attempted route. Waterfall does not infer that a route is free from a provider name, key reference, or missing key. Notices identify role, route/model, and reason when available, and warn that cost or capability may change. Waterfall does not read provider usage or billing totals, so costs are unknown. Errors stay visible; failure logs use bounded request IDs and redacted reasons, never raw prompts, keys, or provider error bodies.

New Main and Support routes default to `credits_only`; `availability` and `manual` are optional. A route's `fallback_on` list overrides the role policy. Legacy Main profiles without a fallback policy retain `availability`. Gateway retries are separate and cannot be observed by Waterfall.

| Failure | Behavior when eligible under the selected policy |
| --- | --- |
| Definite credit exhaustion / HTTP 402 | Marks the account exhausted for configured routes until reset, credential update, or restart. |
| HTTP 429, eligible 500/502/503, Claude 529 | Temporary cooldown, not sticky credit exhaustion. |
| Missing key, HTTP 401 or 404 | Skips the affected route pending reset, configuration, or credential repair. |
| Connection failure | Temporary cooldown. |
| Policy refusal / HTTP 403 | Returns the refusal; never routes around it. |
| Ambiguous timeout / HTTP 504 / partial response or stream | Stops; does not replay through another model. |

Only eligible failures before successful response headers can fall through. An interrupted stream is never replayed. Exhaustion and cooldown state is in memory, not a billing ledger. Routes may share an account and credit pool; separate keys or model names do not prove independent quota. Report account-level exhaustion only when the provider makes that scope clear.

After restoring credits, reset Main with `provider_fallback_reset()` or Support with `provider_fallback_reset(role="support")`. The next request tries the preferred route and announces recovery when successful. Replacing the relevant key or restarting the module also clears exhaustion. A reset does not add credits; failure log entries remain available. The Support listener has no status/reset endpoint. `provider_fallback_status()` reads Main route status; `provider_fallback_models(route_id="...")` lists advertised models for a Main route.

## Optional Jev assistance on Main

`jev_assist` is per Main route and defaults to `false`. It uses Wingman's existing Decision Model/System One interface to narrow the first tool choice on a text turn. Support does not use this option. Configure Wingman's Decision Model first; `jev_min_confidence` defaults to `0.8`. Uncertain decisions keep the full tool list, and tool-result turns get the full catalogue. A selected tool is not argument validation or proof of successful execution. Jev exhaustion falls back to the same Main model until reset; a provider refusal remains a refusal.

## Anthropic Messages routes

Native `anthropic_messages` routes accept nonstreaming requests. Base64 JPEG/PNG/GIF/WebP input is supported; remote image URLs and unsupported content fail explicitly. Thinking and effort settings are forwarded only from explicit route overrides. Opaque signed thinking stays with its original endpoint, secret reference, and model; a fallback receives visible conversation and tool results without those blocks. If a secret is changed to a different provider account, start a new conversation because signatures may be account-specific.

## Return to stock providers

Before disabling Provider fallback or removing its skill, restore the original Core conversation provider and Support Model settings. Turning a Waterfall role off does not rewrite Core's selected endpoint, secret reference, or provider mode. Retain the profile backup and previous skill package until the stock settings work again.


## Optional context budgets

Each BYOK/local route may include `context_window`, `max_output_tokens` and `tool_reserve_tokens`. These are positive integer tokens except tool reserve, which may be zero. Reply plus reserve must be smaller than the configured window. Defaults with an enabled window are a 4,096-token reply cap and 8,192 tokens for tool results. An absent window disables this feature; existing configurations remain unchanged. The hosted `wingman_support` protocol does not accept these settings.

Use the actual served capacity: for a local server, its configured context may be much smaller than the model's advertised training context. Provider/model hard limits still apply. Main and Support have independent routes and budgets. No Core files change.

The initial input allowance is `window - effective reply cap - tool reserve`; an actual tool-result continuation can use `window - effective reply cap`. The effective reply cap is the smaller of the configured cap and any requested cap. Tool definitions, native system prompts and tool results count as input. Explicit thinking budgets must fit inside the reply cap. No history, tool pair or system instruction is silently removed.

The normal installed counter reuses Wingman's tokenizer, with 10 percent padding and 64 structural tokens. When it is unavailable, UTF-8 byte length plus 64 is a conservative fallback estimate. These are preflight estimates, not exact counts for every provider, image or tokenizer. Overflows are returned explicitly, not silently retried on another model or treated as a credit failure. Budget metadata contains counts only, never request bodies or keys.

With a configured primary Main window, guided setup advertises/selects that route's exact model ID in Core. The old `waterfall` alias remains accepted. Wingman infers its own budget from its model table; arbitrary Waterfall limits are not a Core context override. Unknown model IDs may therefore retain Core's 32,000-token estimate. A smaller fallback is separately checked before its request is sent. If the larger conversation cannot fit, it fails clearly rather than losing context. Setup Preview shows the model selection, and Undo restores the previous alias and routes.
